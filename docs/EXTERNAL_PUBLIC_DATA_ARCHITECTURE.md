# External public data architecture — Cloudflare R2 + Neon

Status: approved target architecture; implementation is staged and NOT active in production.

Owner decision:
- Public files: Cloudflare R2.
- Public catalog database: Neon PostgreSQL.
- Media migration: public-only. Confidential files remain on the existing private VPS storage.

## 1. Non-negotiable data boundary

The existing Contabo PostgreSQL database remains the authoritative private business database. It continues to own:
- customer identities and contact details;
- orders, quotations containing customer details, invoices and payment records;
- payment evidence, settlement and reconciliation;
- purchase cost, margins, supplier records and supplier pricing;
- accounting journals, ledgers, tax records and financial reports;
- staff/admin identities, sessions, permissions and audit events;
- private legal documents and all unapproved/draft content.

Neon is a separate public read-model database, not a replacement for the private business database. It may contain only an explicit allowlist of owner-approved public fields:
- product public ID, slug, SKU only if owner approves public exposure;
- English/Nepali product names and descriptions;
- category and brand public names/slugs;
- model, part number, applications and public specifications;
- published selling price/MRP and price display mode;
- public availability label (not exact internal stock or warehouse quantities unless explicitly approved);
- public media URLs, public brochure URLs, SEO fields, publication/update timestamps.

Never copy costPaisa, supplier IDs/details, customer IDs/details, internal stock movement, exact private stock quantities, payment details, tax/accounting records, unpublished fields, staff notes or audit events into Neon.

The public Neon credential must be server-side only. The browser must never receive a Neon connection string or a database role credential. Public website reads must pass through a server-side read-only catalog service or a deliberately limited public API. No public write endpoint is allowed.

## 2. Cloudflare R2 buckets and object policy

Use a dedicated R2 bucket for public website media, served through a custom media hostname (for example, media.bnbmachinery.com) after DNS and domain ownership are verified.

Only owner-approved, published public files are copied to R2:
- product photographs and gallery images;
- company/project gallery images;
- approved public videos;
- public brochures, manuals and price lists.

Keep private media on the existing VPS volume:
- draft/unapproved inventory images;
- payment receipts and bank evidence;
- private product documents;
- supplier/customer attachments;
- legal, accounting and audit documents.

Do not migrate all files. Do not make the existing /data/media volume public. Do not upload a file to R2 merely because its MIME type is an image or PDF: publication state and owner-approved visibility are required.

Object keys must be generated by the server, not accepted as arbitrary paths from the browser. Validate file type, size, extension and content signature. Use immutable/versioned keys for replacement so cache invalidation is predictable. Store the R2 object key and public URL in the private database. Public URLs contain no credentials.

R2 credentials are server-only:
- R2_ACCOUNT_ID
- R2_ACCESS_KEY_ID
- R2_SECRET_ACCESS_KEY
- R2_BUCKET_PUBLIC
- R2_PUBLIC_BASE_URL

Never prefix these values with NEXT_PUBLIC_. Never commit real credentials.

## 3. Neon public catalog

Create a separate Neon project/database for the public catalog. Do not point the existing DATABASE_URL at Neon and do not move the private database.

Recommended public schema tables:
- public_categories
- public_brands
- public_products
- public_product_media
- public_documents (published public documents only)
- public_catalog_sync_state (sync cursor/version only; no private business payload)

Use stable source IDs from the private catalog as external IDs, with unique constraints. Use explicit allowlisted columns, not SELECT * or generic JSON copies. Store prices in integer paisa and include an explicit price mode (FIXED / PRICE_ON_REQUEST); never infer price visibility from a nullable amount alone.

Neon connection setting:
- PUBLIC_CATALOG_DATABASE_URL (server-side only)

Use a dedicated least-privilege Neon role for application reads. A separate writer role is used only by the server-side synchronization worker. No browser-side SQL access, anonymous database credentials, or broad public grants.

## 4. Reliable synchronization

The Contabo private database remains the source of truth. Synchronization is one-way:

Private catalog/admin workflow -> private transactional outbox -> server-side sync worker -> Neon public read model.

On publish/update/unpublish:
1. Save the canonical private product and audit event in the existing transaction.
2. Add an outbox event in the same private transaction.
3. A retryable worker reads pending events.
4. Build an allowlisted public projection from canonical private records.
5. Upsert/delete (or mark unpublished) in Neon idempotently using source ID + version.
6. Mark the outbox event complete only after Neon confirms success.
7. Retry failures with bounded backoff and alert on persistent errors.

Do not dual-write the private database and Neon directly inside a customer-facing request without an outbox. Do not make Neon the source for prices used to charge customers. Checkout/order creation must revalidate current selling price and stock against the private database.

Public site behavior during Neon outage:
- serve the last successfully cached public catalog where safe;
- do not fall back to exposing private records or local unapproved product data;
- show a controlled unavailable state if no safe cached response exists.

## 5. Public-only media migration

Migration must be copy/verify/switch, never move/delete:
1. Inventory all existing media references and classify each file as PUBLIC_APPROVED, PRIVATE, DRAFT/UNAPPROVED or UNKNOWN.
2. Only PUBLIC_APPROVED files are eligible for R2.
3. Copy eligible files to generated R2 keys; keep source files unchanged.
4. Verify object size, MIME type and SHA-256 checksum.
5. Write the R2 key/URL and migration status into metadata.
6. Test anonymous public GET and private-file denial.
7. Switch only the approved public references to R2.
8. Retain source copies until an owner-approved retention period and verified backup exist.
9. Never delete private/draft/unknown files as part of this migration.

Existing `productDocuments.visibility` defaults to PRIVATE. Only explicitly PUBLIC documents attached to a published product may be copied. Existing staff inventory image endpoint currently serves approved/published images through an authenticated-aware route; its visibility and storage adapter must be reviewed before changing public URLs.

## 6. Implementation phases

### Phase A — design/configuration (this PR)
- Record this architecture and security boundary.
- Add placeholder environment variable names only.
- No runtime switch, schema migration, external account access, data copy or production deployment.

### Phase B — infrastructure adapters (separate reviewed PR)
- Add R2 object-storage adapter behind a feature flag.
- Preserve current local private-media adapter.
- Add a separate Neon read-model client; do not replace the private Drizzle client.
- Add unit tests for allowlist projection, private-field exclusion, object-key validation and storage fallback behavior.
- Keep R2/Neon disabled until credentials and test projects are configured.

### Phase C — public catalog outbox/read model
- Add additive private outbox migration.
- Add public Neon schema migration/bootstrap script.
- Add idempotent sync worker and dead-letter/retry visibility.
- Add server-side public catalog read service with caching.
- Keep checkout price/stock validation on the private database.

### Phase D — public media publishing
- Add owner-only publish-to-R2 action.
- Add explicit PUBLIC/PRIVATE visibility for documents with safe defaults.
- Add checksums, immutable object keys and cache headers.
- Do not move private or draft media.

### Phase E — controlled migration and verification
- Dry-run inventory report first.
- Copy only PUBLIC_APPROVED files.
- Verify hashes and public/private access tests.
- Switch public references gradually.
- Obtain owner approval before any old public file cleanup.

### Phase F — production activation
- Configure secrets in the VPS secret environment, not GitHub source files.
- Apply additive migrations only after backup and explicit approval.
- Deploy only after CI, staging acceptance and explicit production approval.
- Keep a rollback path to the current local-media/public-catalog implementation.

## 7. Acceptance criteria

- No customer, supplier, accounting, payment, audit, staff or private legal data exists in Neon.
- No private/draft/unapproved media is present in the public R2 bucket.
- No R2 or Neon secret appears in client bundles, source control, logs or API responses.
- Publishing/unpublishing synchronizes idempotently and retries safely.
- Checkout reads current price/stock from the private database.
- Neon/R2 outage does not expose private data or break admin/accounting.
- Public files are served from the media hostname; VPS disk does not grow with new public uploads.
- Private media remains on private VPS storage and remains protected by existing authentication.
- Backup/restore and migration rollback have been tested before production activation.

## 8. Required owner-provided setup (later)

Create Cloudflare R2 and Neon accounts/projects. Do not send secret keys in chat or commit them. Store credentials directly in the deployment secret manager / VPS environment after the code and staging checks are ready. The owner should provide only non-secret configuration confirmation such as the selected public media hostname and Neon project region.

## Current repository facts

- `lib/server/media-storage.ts` currently stores files under `MEDIA_DIR` (default `/data/media`).
- `infra/docker-compose.yml` mounts the `media` volume at `/data/media`.
- `lib/server/catalog.ts` combines the managed catalog and legacy published inventory records; these sources must be reconciled before the public read model is populated.
- `src/modules/catalog/schema.ts` contains canonical products, product images and product documents. Product documents default to PRIVATE.
- `src/modules/catalog/management.ts` reads canonical product rows including both public and internal fields for admin use. A separate public projection is required; never serialize admin query rows directly.
- `app/api/staff/inventory/route.ts` uploads staff draft images through the private media adapter.
- `app/api/inventory/images/[id]/route.ts` controls staff/public access to legacy inventory image records.

No production migration, deployment, account creation, file copy, public URL switch or deletion is authorized by this design document.
